# Contributing and originality

PourLedger is new hackathon work. Contributions must preserve an auditable line between original project code, user-provided requirements, AI assistance, and third-party dependencies.

## Required practice

1. Do not copy or port application code from previous projects, Juvra, templates, tutorials, or competing submissions.
2. Third-party packages may be used under their licenses, but must be pinned and clearly treated as dependencies rather than claimed authorship.
3. Make one focused change per commit. Include the relevant real build or test result in review notes.
4. Record architectural decisions and rejected alternatives in `docs/` before making large structural changes.
5. A submitting developer must review, understand, and be able to explain every material contract transition and trust statement. AI-assisted work must not be presented as unassisted human authorship.
6. Never fabricate pilot users, wallets, transactions, laboratory results, interviews, traction, or deployment status. Synthetic fixtures stay labelled synthetic.
7. Obtain informed consent before using real project, site, professional, or evidence details. Keep raw documents private by default.
8. Keep QIE Hackathon eligibility, one-submission, wallet, source, documentation, originality, and developer-contribution requirements under owner review before submission.

## Review checklist

- [ ] The change is original to this repository or an identified dependency.
- [ ] The author can explain the state transition and its failure cases.
- [ ] Trust and privacy language remains accurate.
- [ ] Required tests were run and their actual result was recorded.
- [ ] No secret, private key, personal data, or confidential evidence entered Git history.
- [ ] No mainnet/funded-wallet action occurred without explicit approval.
- [ ] Demo, testnet, and live production states are visually and verbally distinct.
